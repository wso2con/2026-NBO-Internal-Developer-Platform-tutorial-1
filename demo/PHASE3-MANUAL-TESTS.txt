 START HERE:  cd <repo>/tutorial-1

 EVERY `make` COMMAND MUST RUN FROM THAT DIRECTORY — it is where the Makefile
 lives. Running make anywhere else gives "No rule to make target", which means
 wrong directory, not broken Makefile. Check with `pwd`.

   STEPS  1-4    Setup — get the stack running
   STEPS  5-7    Automated suites (tests, smoke, hardening)
   STEPS  8-14   POST /applications — the main flow

   STEPS 20-24   GET endpoints

 IN A HURRY? Steps 2, 5, 6, 8 alone show Phase 3 works.

 WHAT PHASE 3 IS
   loan-api  — the public front door (§7.1). Validates, persists, calls
               credit-scoring, publishes to NATS.
   payment-rail-stub — a fake mobile money provider (§7.6). NOTHING CALLS IT
               YET; the disbursement-worker does, in phase 4. It is here so
               that worker has a target ready.

 WHAT STILL FAILS ON PURPOSE
   Scenario 1's disbursement assertions. loan-api approves a loan and publishes
   loan.approved, but the rows in `disbursements` and `repayments` are written
   by the disbursement-worker, which is phase 4. §12 predicts this exactly:
   "Scenarios 1 and 3 pass (disbursement assertions will fail — expected, no
   worker yet)." So `make smoke` exits non-zero at this phase. That is correct.

             nats --server nats:4222 stream info LOANS 2>&1 | grep -i messages

  EXPECT:  Messages: 2   (loan.submitted and loan.approved)


--- STEP 11 ------------------------------------------------------------------
DUPLICATE SUBMISSION — the behaviour the demo rests on (§7.1).
Submit the identical payload again.

  RUN:     curl -s -o /tmp/r2 -w 'HTTP %{http_code}\n' -X POST localhost:8080/applications \
                -H 'Content-Type: application/json' -d @demo/payloads/APP-100244.json

  EXPECT:  HTTP 200          (200 on a duplicate, not 201)
           decided_at unchanged: YES

  The unchanged decided_at proves it did NOT re-score.


--- STEP 12 ------------------------------------------------------------------

--- STEP 15 ------------------------------------------------------------------
All failures are reported together, not just the first.

  RUN:     curl -s -X POST localhost:8080/applications -H 'Content-Type: application/json' \
             -d '{"applicant_name":"","national_id":"","wallet_msisdn":"0712345678",

  EXPECT:  HTTP 400 and SEVEN field errors in one response —
             applicant_name      must not be empty
             national_id         must not be empty
             wallet_msisdn       must match 254 followed by 1 or 7 and 8 digits
             amount_kes          must be between 10000 and 2000000
             term_months         must be one of 6, 12, 24, 36

             employment_months   must not be negative


--- STEP 16 ------------------------------------------------------------------
Amount bounds: 10,000 - 2,000,000 KES inclusive.

  RUN:     for amt in 9999 10000 2000000 2000001; do \
             printf '%10s -> ' "$amt"; \
             curl -s -o /dev/null -w '%{http_code}\n' -X POST localhost:8080/applications \
               -H 'Content-Type: application/json' \
               -d "{\"applicant_name\":\"T\",\"national_id\":\"1\",\"wallet_msisdn\":\"254711111111\",

                    \"employment_months\":12,\"kyc_verified\":true}"; \
           done

  EXPECT:  9999 -> 400,  10000 -> 201,  2000000 -> 201,  2000001 -> 400

  RUN:     docker compose stop credit-scoring
           curl -s -w '\nHTTP %{http_code}\n' -X POST localhost:8080/applications \
             -H 'Content-Type: application/json' \

                  "national_id":"77777777","wallet_msisdn":"254722222222",

                  "employment_months":24,"kyc_verified":true,"existing_defaults":0}'

  EXPECT:  {"message":"scoring service unavailable, application left pending"}
           HTTP 503

  A banking audience will ask about this: an unavailable risk engine produces NO
  decision, never a permissive default.


--- STEP 26 ------------------------------------------------------------------
The record is PENDING with no score, and nothing was published.

  RUN:     psql -c "SELECT application_id, score, decision FROM loan_applications
                     WHERE application_id='APP-PENDING1';"

  EXPECT:  APP-PENDING1 | (null) | PENDING


--- STEP 27 ------------------------------------------------------------------
Bring scoring back; the PENDING record is re-scored on retry.

  RUN:     docker compose start credit-scoring && sleep 12
           curl -s -o /tmp/p2 -w 'HTTP %{http_code}\n' -X POST localhost:8080/applications \
             -H 'Content-Type: application/json' \
             -d '{"application_id":"APP-PENDING1","applicant_name":"Pending Test",
                  "national_id":"77777777","wallet_msisdn":"254722222222",
                  "amount_kes":100000,"term_months":12,"monthly_income":50000,
                  "employment_months":24,"kyc_verified":true,"existing_defaults":0}'
           jq -c '{score,decision}' /tmp/p2

  EXPECT:  HTTP 201 and a real score, e.g. {"score":614,"decision":"DECLINED"}

  See NOTE 2 — this is a deliberate reading of §7.1, not the literal text.

  CLEAN UP:  psql -q -c "DELETE FROM loan_applications WHERE application_id='APP-PENDING1';"

===============================================================================
 NOTES — background, not steps
===============================================================================

NOTE 1 — traceparent travels in the PAYLOAD, not the NATS header
  §8 says every event carries traceparent in the NATS header. ballerinax/nats
  3.3.2 (the latest release) exposes NO header API at all — neither
  AnydataMessage nor JetStreamMessage has a headers field. So traceparent is a
  FIELD IN THE JSON EVENT BODY instead. The outcome §2.6 wants is preserved (the
  trace still crosses the broker unbroken), but phase 4's worker must read it
  from the body. Open with the spec author.

  Inspect an event body:
      docker run --rm --network kifaru_default natsio/nats-box:latest \
        nats --server nats:4222 stream get LOANS 2

NOTE 2 — why a PENDING record is re-scored (step 27)
  §7.1 says a duplicate application_id returns 200 with the existing record and
  does not re-score. Read literally that also applies to a PENDING record — one
  whose scoring call failed — which would strand the loan with no path to a
  decision, forever. So the duplicate rule is applied to DECIDED records
  (APPROVED / DECLINED) only, and a PENDING one is scored on retry. Scenarios 2
  and 3 are unaffected, since both act on decided loans. Open with the spec author.

NOTE 3 — /metrics returns 404 on both Ballerina services
  §7.1 and §7.2 list it, but §3.2 says use Ballerina's BUILT-IN Prometheus
  metrics and add no libraries — and the runtime serves those on its own
  observability port (9797), not the service port. Not a phase 3 checkpoint.

NOTE 4 — images
      loan-api           439MB   (Ballerina; §11 expects 200-300MB, "not worth fighting")
      payment-rail-stub  14.3MB  (Go distroless; §11 allows under 40MB)

NOTE 5 — "error: ... is required but was not set"
  loan-api requires DATABASE_URL, NATS_URL, CREDIT_SCORING_URL and LOG_LEVEL. It
  refuses to start without them, by design (§3.2). To run from source:

      cd app/loan-api
      LOG_LEVEL=info DATABASE_URL=postgres://kifaru:kifaru_local_only@localhost:5432/kifaru \
      NATS_URL=nats://localhost:4222 CREDIT_SCORING_URL=http://localhost:8081 bal run
      cd -

  `make test` supplies placeholders for you. loan-api connects to the database
  and NATS LAZILY — on first use, not at startup — so the unit tests need
  neither running.

NOTE 6 — what phase 4 changes
  disbursement-worker consumes loan.approved, claims the loan in Valkey, calls
  payment-rail-stub, writes the disbursement row and generates the repayment
  schedule. Step 6's scenario 1 goes green, scenario 2 becomes assertable, and
  step 20's disbursement/instalments stop being null/0.
