 PHASE 2 TEST STEPS — credit-scoring service
 26 numbered steps. Run them in order. Each has RUN: and EXPECT:.
===============================================================================

 START HERE:  cd <repo>/tutorial-1

 EVERY `make` COMMAND MUST RUN FROM THAT DIRECTORY — it is where the Makefile
 lives. Running make anywhere else gives:

     make: *** No rule to make target `test'.  Stop.

 That means "wrong directory", not "broken Makefile". Check with `pwd`; the
 path must end in /tutorial-1. A few steps below cd into a service directory —
 come back before the next make command.

   STEPS  1-3    Setup — get it running

===============================================================================
 SCORING BEHAVIOUR
===============================================================================
 Each step starts from APP-100244 (which scores 712) and changes exactly ONE
 field, so any change in score is attributable to that one rule.

 Define this helper once, then steps 13-16 are one-liners:

   score() { curl -s -X POST localhost:8081/score \
               -H 'Content-Type: application/json' -d "$1" | jq -c '{score,decision}'; }


--- STEP 13 ------------------------------------------------------------------
KYC not verified — costs 120 points (+40 becomes -80).

  RUN:     score '{"application_id":"APP-T1","amount_kes":250000,"term_months":24,
                   "monthly_income":96000,"employment_months":30,
                   "kyc_verified":false,"existing_defaults":0}'

  EXPECT:  {"score":592,"decision":"DECLINED"}          712 - 120 = 592


--- STEP 14 ------------------------------------------------------------------
One prior default — costs 150 points AND adds a sixth factor.

  RUN:     curl -s -X POST localhost:8081/score -H 'Content-Type: application/json' \
             -d '{"application_id":"APP-T2","amount_kes":250000,"term_months":24,
                  "monthly_income":96000,"employment_months":30,
                  "kyc_verified":true,"existing_defaults":1}' \
             | jq -c '{score,decision,factors:[.factors[]|.name]}'

  EXPECT:  score 562, DECLINED, factors
           ["base","income","employment","affordability","kyc","defaults"]

  CHECK:   the "defaults" factor appears ONLY when it applies, so the happy
           path in step 7 stays at five factors.


--- STEP 15 ------------------------------------------------------------------
Unaffordable loan — DTI crosses 0.50, affordability swings to -100.

  RUN:     score '{"application_id":"APP-T3","amount_kes":500000,"term_months":12,
                   "monthly_income":60000,"employment_months":24,
                   "kyc_verified":true,"existing_defaults":0}'

  EXPECT:  {"score":384,"decision":"DECLINED"}
           full reason reads "Affordability insufficient (DTI 0.82)"


--- STEP 16 ------------------------------------------------------------------
The score floor — five defaults would take it far below 300.

  RUN:     score '{"application_id":"APP-T4","amount_kes":300000,"term_months":24,
                   "monthly_income":38000,"employment_months":24,
                   "kyc_verified":true,"existing_defaults":5}'

  EXPECT:  {"score":300,"decision":"DECLINED"}
           clamped at the 300 floor, never negative.


--- STEP 17 ------------------------------------------------------------------
Determinism — the property the whole demo leans on.

  RUN:     for i in $(seq 1 20); do \
             curl -s -X POST localhost:8081/score -H 'Content-Type: application/json' \
                  -d @demo/payloads/APP-100244.json | jq -c '{score,decision}'; \
           done | sort -u

  EXPECT:  exactly ONE line:  {"score":712,"decision":"APPROVED"}
           More than one line means something non-deterministic crept in.


--- STEP 18 ------------------------------------------------------------------
Bad input is rejected with field-level errors.

  RUN:     curl -s -X POST localhost:8081/score -H 'Content-Type: application/json' \
             -d '{"application_id":"APP-BAD","amount_kes":250000,"term_months":24,
                  "monthly_income":0,"employment_months":30,
                  "kyc_verified":true,"existing_defaults":0}' | jq .

  EXPECT:  {
             "message": "validation failed",
             "errors": [
               { "field": "monthly_income", "message": "must be greater than 0" }
             ]
           }

 CONFIGURATION FAILURES
===============================================================================
 §3.2: config is read and range-checked ONCE at startup, before the listener
 starts. A bad value must name the variable and exit non-zero. Each step runs a
 throwaway container and prints its exit code.


--- STEP 19 ------------------------------------------------------------------
Required variable missing.  [CHECKPOINT 4 of 4]

  RUN:     docker run --rm -e LOG_LEVEL= kifaru/credit-scoring:local; echo "exit=$?"

  EXPECT:  error: LOG_LEVEL is required but was not set
           exit=1


--- STEP 20 ------------------------------------------------------------------
Required variable present but invalid.

  RUN:     docker run --rm -e LOG_LEVEL=verbose kifaru/credit-scoring:local; echo "exit=$?"

  EXPECT:  error: LOG_LEVEL must be one of debug|info|warn|error, got 'verbose'
           exit=1


--- STEP 21 ------------------------------------------------------------------
Optional variable, unparseable.

  RUN:     docker run --rm -e PORT=abc kifaru/credit-scoring:local; echo "exit=$?"

  EXPECT:  error: PORT must be an integer, got 'abc'
           exit=1


--- STEP 22 ------------------------------------------------------------------
Optional variable, out of range.

  RUN:     docker run --rm -e PORT=99999 kifaru/credit-scoring:local; echo "exit=$?"

  EXPECT:  error: PORT must be between 1 and 65535, got 99999
           exit=1

  In steps 19-22 the listener never binds — the failure happens in init(),
  before any port opens. Fail at startup, not at first request.


--- STEP 23 ------------------------------------------------------------------
Logs are structured JSON on stdout, carrying application_id.

  RUN:     docker compose logs credit-scoring | tail -5

  EXPECT:  {"time":"...", "level":"INFO", "module":"kifaru/credit_scoring",
            "message":"credit-scoring started", "port":8081,
            "log_level":"info", "approval_threshold":650}
           {"time":"...", "level":"INFO", ..., "message":"application scored",
            "application_id":"APP-100244", "score":712, "decision":"APPROVED"}

  CHECK:   the startup line proves which settings the process actually came up
           with, and every loan-related line carries application_id (§2.5).

--- STEP 25 ------------------------------------------------------------------
Confirm it really runs as a non-root NUMERIC uid.

  RUN:     docker run --rm --entrypoint sh kifaru/credit-scoring:local -c 'id'

  EXPECT:  uid=10001 gid=10001 groups=10001

  Numeric, not a name — Kubernetes runAsNonRoot cannot verify a username (§11).


--- STEP 26 ------------------------------------------------------------------
Confirm the root filesystem is genuinely read-only.

  RUN:     docker run --rm --read-only --tmpfs /tmp --user 10001:10001 \
             --entrypoint sh kifaru/credit-scoring:local \
             -c 'touch /probe 2>&1; touch /tmp/probe && echo "tmp writable OK"'

  EXPECT:  touch: cannot touch '/probe': Read-only file system
           tmp writable OK

  Nothing is written at runtime except /tmp. The JVM needs a writable temp dir,
  which is why /tmp is tmpfs and java.io.tmpdir points at it — without that the
  JVM will not start read-only.


===============================================================================
 NOTES — background, not steps
===============================================================================

NOTE 1 — "error: LOG_LEVEL is required but was not set"
  This is the most common surprise, and it is CORRECT behaviour (it is what
  step 19 tests). §3.2 requires failing loudly at startup rather than silently
  defaulting. To run locally:

      cd app/credit-scoring && LOG_LEVEL=info bal run

  `bal test` hits it too, because it executes module init(). `make test` sets
  the variable for you. The container never hits it — the Dockerfile sets
  LOG_LEVEL=info as a default.

NOTE 2 — why there is no Config.toml
  §3.2 forbids one: a config file baked into the image cannot vary across the
  three environments the same image is promoted through. JSON logging is turned
  on with the env var BAL_CONFIG_VAR_BALLERINA_LOG_FORMAT=json instead, set in
  the Dockerfile. Locally, add it to see the same output:

      LOG_LEVEL=info BAL_CONFIG_VAR_BALLERINA_LOG_FORMAT=json bal run

NOTE 3 — /metrics returns 404  (known deviation, open with the spec author)
  §7.2 lists /metrics as a service endpoint, but §3.2 says use Ballerina's
  BUILT-IN Prometheus metrics and add no libraries — and the runtime serves
  those on its own observability port (9797), not on 8081. Not a Phase 2
  checkpoint.

NOTE 4 — image size 375MB  (known deviation)
  §11 expects "roughly 200-300MB" and says it is not worth fighting. The
  runtime image carries only a slim JRE plus the jar; the ~1GB Ballerina
  distribution stays in the builder stage.

      docker images kifaru/credit-scoring:local --format '{{.Size}}'

NOTE 5 — rebuilding after a code change

      make up                                    # rebuilds what changed
      docker compose up -d --build credit-scoring  # or just this service

NOTE 6 — where this runs
  Everything runs inside the Colima VM (6 CPU / 10 GiB). Ports are forwarded,
  so localhost:8081 works from macOS directly. If docker commands fail after a
  reboot the VM is stopped, not broken — `colima start`, or `make doctor` will
  tell you which.

NOTE 7 — what Phase 2 does NOT cover
  loan-api calling this service (phase 3), the full smoke script (phase 3
  onward), NATS, the database, and the arrears job. Phase 1's data-layer steps
  are in demo/PHASE1-MANUAL-TESTS.txt and still apply.
